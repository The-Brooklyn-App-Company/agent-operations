# Transmogrify v2: migration plan

**Status:** plan, not started (2026-11-19). Nothing has been pushed to the
Transmogrify repository. This file moves there with the kit and is deleted
from this repository once v2 lands. The plan was written after reading the
Transmogrify v1 source read-only; every v1 name below is from that source.

## Why

Agent Operations (this kit) and Transmogrify v1 solve two halves of one
problem. The kit runs a small, accountable team of long-lived agent
sessions across Claude Code and Codex: rules, homes, the mailroom with its
degradation ladders, the supervisor, lane switching, the guided first run
and the operator routines. Transmogrify v1 is a skill that lets either app
spawn, steer, harvest and retire short-lived **worker lanes** in the other
app, with exact ownership and durable operation records. Adopters should
not have to discover two projects, two installers and two vocabularies. v2
puts both under the Transmogrify name: one install, one first run, one
skill index.

History: import the kit with `git subtree add --prefix=ops` (or a merge of
an unrelated history into a subfolder) so every kit commit stays reachable
and blame keeps working. No squash.

## What of v1 to keep

Keep, as the **workers** layer under the operations layer:

- **The lane lifecycle** (`scripts/lane.js`: spawn, steer, status, stop,
  recover, harvest, retire, reconcile) with exact ownership, journaled
  mutations and "never replay an unknown outcome". It is the kit's missing
  worker mechanism (K-23, K-25): operators delegate to v1 lanes instead of
  ad-hoc headless runs, and the kit's K-28 reconciliation in the mailroom is
  the same discipline.
- **The doctor and guided setup** (`scripts/doctor.js`, `scripts/setup.js`,
  `setup.ownerActions` with its `blocking` flag, one consent at a time).
  This and the kit's `bootstrap.sh` become one first run: the doctor's plan
  gains the kit's host steps (`install.sh host`, read-only first) and
  `bootstrap.sh`'s in-app checklist becomes owner actions.
- **The one-line start prompt pinned to a release commit**, generated by CI
  and refusing to fall back to a branch.
- **The output contract** (`docs/OUTPUT.md`: fixed exit codes, one JSON
  envelope on failure, allowlisted success output) for the Node tools; the
  sh tools keep the kit's exit codes, which already line up (0, 1, 2, 3).
- **Execution profiles** (`docs/EXECUTION-PROFILES.md`: intent to model,
  effort and speed, compiled against the provider's catalog, failing closed,
  immutable per lane). They become the one place model choice is resolved:
  the kit's `operator.conf` model lines (decided at creation) and the
  `implementer_*` / `reviewer_*` profile keys map onto them.
- **The `::: ` title marker** for worker lanes, kept distinct from operator
  titles and the "Mailroom" title.
- **Dated compatibility receipts** per client build: the same discipline as
  the kit's "What is proven" table, the client-capabilities evidence levels
  and the mailroom's version fingerprint.
- **Open-source scaffolding**: `SECURITY.md`, `CODE_OF_CONDUCT.md`,
  `CONTRIBUTING.md`, the issue and pull-request templates, Dependabot, the
  pinned CI workflows, and the site with its budgets and checks.

Retire or fold in:

- v1's per-parent **watch and wake channels** (`watch.js`,
  `lane-status-listen.js`, `docs/NOTIFICATIONS.md`) overlap the mailroom.
  In v2 a worker's completion becomes a note to its parent's inbox,
  delivered by the mailroom's ladders: one delivery path, one telemetry
  format.
- The **desktop attachment** machinery (`desktop-attach.js`) stays optional
  and off by default, with its "no verified build" status stated plainly.
- v1's support and security contacts are reviewed before reuse.

## New in v2: approvals that follow the operator

An owner requirement: approvals must keep working when an operator moves
between Claude Code and Codex, translated natively and kept in sync, as
part of the package's job. Today the kit records standing grants in each
`MANDATE.md` and `hygiene.sh` checks them against Claude Code's permission
rules only.

1. **One client-neutral grants file** in the Oracle home (and per operator
   where scoped). Each grant: a stable id; the owner's verbatim words and
   the date; scope; limits; what it does not cover; expiry. Generic
   examples only in the repository; real grants live in private homes.
2. **A renderer** into each client's native approval layer, every entry
   tagged with its grant id:
   - Claude Code: `autoMode.allow` entries in the home's settings.
   - Codex: the `[auto_review].policy` configuration. **TBD**: the exact
     mechanism and format are still being confirmed; the renderer ships
     for Codex only once they are.
   The kit today never edits a client's settings; whether the renderer
   writes them or produces a file the human applies is a design decision
   to settle with the owner before building.
3. **A drift check** (grants file against each client's rendered layer):
   run by the nightly hygiene job, by the first run, and by the client
   switch routine, which **refuses to switch** an operator until the
   target side's approvals match.

## Also folded in from the kit's 0.3.1

- [Client capabilities](client-capabilities.md): the operation-by-operation
  mapping becomes the adapter contract for both layers (v1's adapters
  already follow "lifecycle parity, not transport symmetry").
- Client-neutral recovery: one digest renderer, per-client hook adapters
  (`SessionStart` sources `startup|resume|compact|fork` on Codex, hook
  trust, a token budget as well as a byte cap), an explicit re-read until
  verified, and a bounded current-state block instead of a notes tail.
- Switch and routine receipts carry the app's own readback (pins, model) or
  a stated gap; an acknowledgement proves receipt only.
- The schedule inventory's fields (mechanism, native id, owner and side,
  timezone, paused state, last verified) cover v1's maintenance jobs too.

## The new public README (outline)

Polished, for adopters; plain English, no internal names, fictional
examples only, every claim dated or marked unverified, no AI attribution.

1. **What it is, in one paragraph:** an operating kit plus a worker-lane
   skill for Claude Code and Codex on your own always-on machine; who it is
   for (a person or a small team); what it is not (a framework, a hosted
   service, a daemon you trust with credentials).
2. **The picture:** the Oracle, operators, workers and reviewers; one
   diagram of the layers (sources, inbox, relay, bridges, lanes, workers)
   and the two degradation ladders.
3. **Install in one line:** the pinned start prompt; from source,
   `./install.sh`, then the one guided first run (doctor plus host setup),
   which ends with the short list of in-app steps.
4. **Your first hour:** the Oracle comes up, `operator.sh create` adds an
   operator (models decided once), a cross-app note arrives, `mailroom.sh
   metrics` shows the tier it took, a worker lane runs and hands back a
   commit.
5. **Guarantees and defaults:** claim only what is proven; approvals go
   through the Oracle and follow an operator across clients; degrade, never
   stop (a broken tier adds latency and raises one flag); one active side;
   models set at creation; secrets store to store; no AI attribution.
6. **Support matrix:** clients, desktop apps, OS, with dated receipts and
   what is unverified.
7. **Concepts:** rules (`K-nn`), homes, the mailroom, routines and switches,
   workers and execution profiles, grants, review.
8. **Tools:** one table for `ops/` (sh), one for the Node tools.
9. **Security model:** local control planes only; the opt-in undocumented
   interfaces (the Claude peer socket, the Codex app tool server) and what
   each reads; what the grants renderer may write.
10. **Documentation map, roadmap, contributing, license.**

## Steps to land v2

1. Merge this kit's 0.3.1 pull request first, after its live acceptance
   (the mailroom tests in `TESTING.md`), so v2 starts from a reviewed,
   tagged kit.
2. In a branch of the Transmogrify repository: import the kit history under
   `ops/` (subtree), move docs and skills as in the table, rewrite links,
   and keep both suites green: v1's Node tests unchanged, the kit's suite
   as a new CI job under sh and dash, plus `shellcheck` and `check.sh kit`.
3. One first run: the doctor gains read-only host checks (`ops/install.sh
   host`) and owner actions for `--apply` and each in-app step; `setup.js`
   runs `--apply` only with consent. Keep `bootstrap.sh` as the sh entry
   point that calls the same steps.
4. Route worker completions through the mailroom (a note to the parent's
   inbox) behind a setting, prove it against fakes, then make it the
   default and remove v1's separate wake path (K-36: build alongside, then
   switch).
5. Grants: the file format and the drift check first (read-only, with
   fakes for both clients); the Claude renderer next; the Codex renderer
   once its mechanism is confirmed; the switch refusal last.
6. Write the new README and fold `SKILL.md` and the kit's skills into one
   index; update the site's content from the README.
7. Privacy pass before publishing: a local denylist scan plus a read by a
   model that has not seen private sources; cross-family review within
   three rounds (K-19, K-20).
8. Release 2.0.0 with a migration note for kit users (`ops/` paths,
   unchanged profile keys) and v1 users (lane commands unchanged). Archive
   this repository with a pointer.
